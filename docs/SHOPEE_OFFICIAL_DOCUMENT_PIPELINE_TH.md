# ฐานข้อมูลและการตรวจเอกสารทางการของ Shopee

อัปเดต: 10 กันยายน 2569 (Asia/Bangkok)

เอกสารนี้เป็นบันทึกทางเทคนิคใน repository ไม่ใช่ข้อความสำหรับแสดงบนหน้าเว็บ

## ปัญหาที่ระบบนี้แก้

อีเมล Shopee เหมาะกับ timeline และงานเกือบเรียลไทม์ แต่ไม่มีส่วนลดจาก Shopee,
การยกเลิกอัตโนมัติ, การคืนเงิน/คืนสินค้า และสถานะล่าสุดครบทุกกรณี จึงใช้ข้อมูลจาก
อีเมลเพียงอย่างเดียวคำนวณให้ตรงกับ Business Insights ไม่ได้

ระบบต้องดาวน์โหลดและนำเข้ารายงานทางการเป็นประจำ โดยไม่ scrape ตัวเลขที่แสดงบน
หน้าจอและไม่ให้ LLM ตัดสินยอด:

- Business Insights
- คำสั่งซื้อทั้งหมด (Order All)
- รายงานการเงิน (Financial Statement)
- Seller Balance
- รายละเอียดรายรับของฉัน — โอนเงินแล้ว
- รายละเอียดรายรับของฉัน — รอดำเนินการ เมื่อ Shopee เปิดให้ export
- คำสั่งซื้อที่ยกเลิก / คืนเงินหรือคืนสินค้า / จัดส่งไม่สำเร็จ

## ห้ามปนฐานวันที่

1. Business Insights เป็น source of truth ของ “ยอดขาย” และ
   “คำสั่งซื้อ(ได้รับการยืนยัน)” ตามวันที่ในรายงาน Shopee ผู้ใช้เลือกช่วงวันที่ใด
   ระบบต้องรวม daily facts ของช่วงเดียวกันแบบ inclusive เท่านั้น
2. Order All และ ZIP ยกเลิก/คืนสินค้าใช้วันที่สร้างคำสั่งซื้อเวลาไทย
3. รายงานการเงิน, รายละเอียดรายรับของฉัน และ Seller Balance ใช้รอบเงินโอน
   รายสัปดาห์ เป็นหลักฐานบัญชี ไม่ใช่ยอดขาย Business Insights
4. วันที่ยื่นคำขอคืนเงินอาจอยู่หลังวันที่สร้างคำสั่งซื้อ จึงต้องใช้ rolling 31 วัน
   และข้อมูลล่าสุดทับสถานะเก่าโดยไม่แก้หลักฐานต้นฉบับ

## กฎตรวจเงินโอนรายสัปดาห์

รอบหนึ่งถือว่า `source_backed` ต่อเมื่อ:

```text
รายงานการเงิน: จำนวนเงินที่โอนแล้วทั้งหมด
= รายละเอียดรายรับของฉัน (โอนเงินแล้ว): จำนวนเงินทั้งหมดที่โอนแล้ว
= Seller Balance: ผลรวมรายการทำสำเร็จที่มีหมายเลขคำสั่งซื้อ
```

นอกจากยอดรวมต้องตรงกันแล้ว คู่ `(หมายเลขคำสั่งซื้อ, จำนวนเงิน)` ต้องตรงแบบ
multiset ด้วย จึงไม่ยอมรับกรณียอดรวมบังเอิญเท่ากันแต่คนละคำสั่งซื้อ

- แถวรายละเอียดรายรับที่ยอดโอน `฿0` ไม่มีรายการรับเงินคู่กันใน Seller Balance;
  ให้นับและแสดงแยก ไม่ถือว่าเอกสารขาด
- รายการ Seller Balance ที่ไม่มีหมายเลขคำสั่งซื้อ เช่น ค่ารับพัสดุหรือรายการปรับยอด
  ให้แสดงเป็น “รายการปรับยอดใน Seller Balance” แยกจากยอดเงินตามรายงานการเงิน
- หากเอกสารสามชนิดขาดอย่างใดอย่างหนึ่ง ผลเป็น `incomplete`
- หากเอกสารครบแต่ยอดหรือคู่คำสั่งซื้อไม่ตรง ผลเป็น `mismatch`

ตัวอย่างจริงรอบ 31 ส.ค.–6 ก.ย. 2569:

- SC Drug Store: รายงานการเงิน/รายละเอียดรายรับ/Seller Balance ตรงกัน ฿76,618;
  รายละเอียดรายรับ 417 แถว และ Seller Balance 416 แถว เพราะมียอดโอน ฿0 หนึ่งแถว
- DR.Morepen: ทั้งสามแหล่งตรงกัน ฿3,231; Seller Balance มีรายการปรับยอด -฿30
  ซึ่งไม่เกี่ยวกับคำสั่งซื้อและไม่หักออกจากยอดรายงานการเงิน

## กฎของ ZIP ยกเลิก/คืนสินค้า

ชื่อ `Order.return_refund_cancel.20260809_20260909.zip` หมายถึงวันที่สร้าง
คำสั่งซื้อ 9 ส.ค.–8 ก.ย. 2569 เพราะวันท้ายในชื่อเป็น exclusive upper bound

เก็บเฉพาะข้อมูลที่จำเป็นต่อบัญชีและการตรวจสถานะ ได้แก่ หมายเลขคำสั่งซื้อ,
หมายเลขคำขอ, วันที่, สถานะ, เหตุผล และจำนวนเงินตามชื่อคอลัมน์ Shopee เดิม
ห้ามเก็บชื่อผู้ซื้อ, username, เบอร์โทร หรือที่อยู่ลงฐานข้อมูล

จำนวนเงินแต่ละกลุ่มต้องใช้ชื่อตาม Shopee และห้ามนำไปแทนยอดขาย Business Insights:

- คำสั่งซื้อที่ยกเลิก / จัดส่งไม่สำเร็จ: `ราคาขายสุทธิ`
- คืนเงิน/คืนสินค้า: `จำนวนเงินคืนทั้งหมด`

## ความปลอดภัยและ audit

- เก็บ `download.suggestedFilename()` เป็น `originalFilename`
- ตรวจร้าน, ช่วงวันที่, ชนิดไฟล์, magic bytes, workbook/PDF/ZIP structure และ SHA-256
- แยก browser profile, download root และ durable upload queue ของสองร้าน
- import เป็น transaction และ replay hash เดิมได้ `unchanged`
- backend รับผ่าน dedicated bearer token และ fail closed เมื่อไม่มี secret
- งานนี้ไม่สั่งพิมพ์และไม่ส่ง LINE

Migration `020_shopee_official_documents.sql` เพิ่มตารางหลักฐานแบบ immutable และ
ขยาย ingest audit ให้รองรับเอกสารทุกชนิดข้างต้น หลังติดตั้ง agent รุ่นใหม่ ระบบจะ
สร้าง ingest job ย้อนหลังจาก completed manifests ที่มีหลักฐานชื่อเดิม/hash ครบ
โดยไม่ดาวน์โหลดไฟล์เดิมซ้ำ
