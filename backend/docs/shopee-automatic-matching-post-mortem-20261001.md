# Shopee → AdaSmart: repeated mapping review, 2026-10-01

## เกิดอะไรขึ้น

สินค้าเดิมกลับเข้ารายการตรวจสอบเมื่อร้านเปลี่ยนชื่อประกาศ รวมหลายสูตรในประกาศเดียว หรือเขียนตัวเลือกด้วยรูปแบบใหม่ ระบบเดิมรู้จักร้าน + ชื่อ + ตัวเลือกที่ตรงกับ catalog/alias และกฎคัดลอกที่บันทึกไว้ จึงจำข้อความเดิมได้ แต่ยังใช้ข้อเท็จจริงที่ยืนยันแล้วกับชื่อใหม่ไม่ได้ ผู้ใช้ต้องยืนยันสินค้าและแพ็กเดิมซ้ำ การเพิ่ม exact rule แก้แต่ละครั้งได้ แต่ไม่ได้แก้สาเหตุที่ต้องทำซ้ำ

ผลกระทบคือรายการใหม่อาจมี SKU หรือหน่วยไม่ครบ ตารางคัดลอกจะยังไม่พร้อม แม้เป็นสินค้าซึ่งเคยยืนยันมาก่อน การเทียบยอด Business Insights ช่วยตรวจยอดเงิน แต่ไม่ใช่หลักฐานว่าสินค้าหรือจำนวนต่อแพ็กถูกต้อง

## ตรวจเส้นทางข้อมูลก่อนแก้

- Catalog มี `productId`/`variationId` ของ Shopee แต่รายการใน OrderAll และ email ที่ผ่าน `sanitizeShopeeOrderItem` เก็บเพียง `name`, `variant`, `quantity`, `unitPrice` ไม่มี ID หรือบาร์โค้ดที่สังเกตจากคำสั่งซื้อนั้น
- `listingProductId`/`listingVariationId` ใน `productMatch` มาจาก catalog หลังจับคู่ ไม่ใช่รหัสต้นทางที่นำมาพิสูจน์การจับคู่ได้อีกครั้ง
- งานนี้จึงไม่เพิ่มคอลัมน์ต้นทางที่ยังไม่มี ไม่เปลี่ยน fingerprint/schema ของข้อมูลนำเข้า และไม่อ้างว่าการจับคู่ด้วย ID ทำงานกับคำสั่งซื้อจริงแล้ว

## สิ่งที่แก้

เพิ่ม `shopeeVerifiedCopyMatcher.js` ในเส้นทาง `resolveCopyProduct` ของตารางคัดลอกจริง:

1. ใช้ exact override และผล catalog เดิมก่อน รวมถึง bundle, visibility และข้อค้างยืนยันหน่วย ไม่มี fallback มาปลด hold ของผล catalog ที่รู้จักแล้ว
2. ถ้ายัง unmapped ลองรูปแบบข้อความที่เทียบเท่ากัน เช่น ตัวพิมพ์ใหญ่/เล็ก full-width ASCII ช่องว่าง เครื่องหมายคั่น `มล.`/`ml` และ `6 × 7 cm`/`6x7 ซม.` **คงลำดับตัวเลขและหน่วย** จึงไม่ถือว่า `1 กล่อง 12 ซอง` เท่ากับ `12 กล่อง 1 ซอง`
3. ถ้ายังไม่ตรง ใช้ parser แยกข้อมูลตามตระกูลที่รองรับ: SOS, Propoliz mouth spray, I-Herb, BACTIGRAS, One Gerd และ Deeday Fiber Fiber ไม่ใช้คะแนนความคล้ายของชื่อ
4. สร้าง candidate จากกฎที่ยืนยันไว้และ ERP master โดยอัตโนมัติ รวม catalog ที่มีหลักฐานหน่วยฐาน/ตัวคูณครบ ไม่มีตารางใหม่ที่ hardcode ชื่อใหม่ให้ SKU ใหม่ ต้องเหลือคำตอบเดียวทั้ง SKU หน่วย ERP และตัวคูณจึงคัดลอกได้
5. ชื่อใหม่ต้องระบุข้อมูลสำคัญชัดเจน: สูตร/ขนาด/รุ่น/หน่วยขาย/แพ็ก ตัวเลือกในชื่อรวมที่เคยยืนยันแล้วใช้บริบทเดิมได้ แต่สูตรหรือแพ็กใหม่ไม่มีสิทธิ์สืบทอดจากสินค้าอื่นที่ชื่อคล้ายกัน
6. เพิ่มข้อความเหตุผลภาษาไทยใน review และ metadata `matchingReview` สำหรับข้อมูลขาด แพ็กไม่ตรง หรือหลักฐานขัดกัน Candidate เป็นข้อเสนอสำหรับตรวจต่อ ไม่ใช่การรับรองรหัสนั้น
7. เก็บ `matchingProvenance` กับแถวต้นทางที่จับคู่อัตโนมัติ: algorithm version, method, source anchor, authority และหลักฐานเดิม ชื่อ/ตัวเลือก/จำนวนซื้อ/เงินต้นทางยังเหมือนเดิม เพิ่ม `matchingAlgorithmVersion` บน copy plan และรวม digest ของ version + กฎ + master + unit holds ใน catalog digest เพื่อให้ cache ประเมินใหม่เมื่อเปลี่ยนหลักฐาน

ตัวอย่างพฤติกรรมใหม่ที่ทดสอบด้วยข้อมูลสมมุติ:

| ข้อมูลที่เขียนใหม่ | ผลจากหลักฐานเดิม |
| --- | --- |
| `Kids Propoliz Mouth Spray 10ml` / `1 bottle` | รุ่นเด็ก 10 มล. หนึ่งขวด ERP; ไม่ปนกับ 15 มล. |
| `SOS Plus S Series` / `M 4x7 cm 1 box` | กล่อง S; รุ่น T ขนาดเดียวกันเป็นคนละ SKU |
| `One Gerd mint 10 ml` / `1 box 12 sachets` | 12 ซอง ERP; กล่อง 24 ซองไม่ผ่าน |
| `Deeday Fiber Fiber 18 grams` / `1 box 10 sachets` | 10 ซองตามแพ็กที่ยืนยัน; ชื่อใหม่ไม่ระบุแพ็กยังค้างตรวจ |
| `BACTIGRAS 10x10 cm 10 sheets/box` / `4 boxes` | 40 แผ่น โดยใช้หลักฐานกล่องเดิม 10 แผ่น ไม่เดาจากราคา |

ถ้าผู้เรียกส่ง ID/บาร์โค้ดเข้าฟังก์ชันโดยตรง จะตรวจความขัดแย้งด้วย ID ต้องชี้ catalog record ที่ยืนยัน SKU **และจำนวน/หน่วยขายเดียวกัน**; ID ของซองเดี่ยวไม่รับรองกล่องหลายซอง บาร์โค้ดหน่วยฐานไม่รับรองบาร์โค้ดกล่อง และบาร์โค้ดอย่างเดียวไม่ทำให้จับคู่สินค้าได้ การตรวจนี้เตรียมไว้ป้องกันข้อมูลขัดกัน ไม่ใช่การเพิ่ม ID ingestion ให้ระบบปัจจุบัน

## หลักฐานและสิ่งที่ไม่ได้เปลี่ยน

ข้อเท็จจริงถาวรยังอยู่ใน `shopeeAdaSmartCopyRules.v1.json`, catalog, unit-validation และ master evidence เดิม รวม StockDay SC004 วันที่ 30/09/2026 (SHA-256 `e5fb358d36946bda528db9c6c99836ba43800bf137ed768528bdde47c2454afe`) ไม่ใช้สต๊อกหรือราคา ERP เพื่อตัดสินตัวสินค้า

ไม่ได้แก้ financial allocation, seller voucher, Shopee-funded discount, business-date corrections, order cohort, Business Insights blocking หรือการแบ่งราคาถึงสตางค์ ไม่มีการแก้คำสั่งซื้อต้นทางหรือเขียนเอกสาร AdaSmart ไม่มีข้อมูลลูกค้า เลขคำสั่งซื้อ หรือยอดเงินจริงในเอกสารนี้

## Validation ledger

- `shopee-verified-copy-matcher.test.cjs`: ชื่อที่เปลี่ยนจริงในเชิงโครงสร้าง, ไทย/อังกฤษ, series/model/dimensions, สูตร/ขนาด, การคูณจำนวนกล่องที่เหมือนเดิม, การแยกซองซิป/ปกติ/OTC, ข้อมูลขัดกัน, bundle, shop boundary, authority hold, ID ของ SKU เดียวกันแต่คนละแพ็ก และบาร์โค้ดผิด
- ทดสอบ sanitized → catalog enrichment → copy plan จริง แสดงว่าชื่อใหม่ยัง unmapped ใน catalog แต่ตารางคัดลอกใช้หลักฐานใหม่ได้ และเก็บค่าสินค้า/จำนวน/เงินต้นทาง พร้อมบล็อกเมื่อ BI ยอดหรือจำนวนออเดอร์ไม่ตรง
- Developer validation: 10 mapping/copy suites / 272 tests และ 7 dependent suites / 94 tests ผ่าน รวม 17 suites / 366 tests (66 tests อยู่ใน matcher suite ใหม่); `git diff --check` ผ่าน
- Root review พบและส่งกลับให้แก้ 2 จุดก่อนรับงาน: การเรียงคำเพื่อ normalize ทำให้ความสัมพันธ์เลข/หน่วยหาย และการเช็ก stable ID เฉพาะ SKU ยังไม่แยกซองเดี่ยวกับกล่อง ผู้เขียนแก้ให้คงลำดับข้อความและตรวจตัวคูณแพ็กของ catalog record พร้อมเพิ่ม regression tests ทั้งสองกรณี
- Root reviewer ทดสอบอิสระ 28 กรณีผ่านทั้งหมด: ชื่อที่เขียนใหม่และข้อมูลครบ 12 กรณีจับคู่ถูก พร้อมรักษาสตางค์และแยกร้าน; ข้อมูลกำกวม/ขัดกัน/แพ็กเปลี่ยนอีก 16 กรณียังค้างตรวจและปิดคอลัมน์คัดลอก
- เทียบ frozen baseline 122 day/shop plans: ทั้ง 122 แผนยังพร้อมคัดลอก และ columns, SKU, quantities, unit prices, source amounts, totals และ order counts เหมือนก่อนแก้ ไม่มีวันที่เดิมเปลี่ยนผล การเพิ่ม provenance/version ไม่ถูกนับเป็นการเปลี่ยนตัวเลข
- Full Linux CI และการยืนยัน deployment เป็น gate ของ root reviewer; ยังไม่อ้างผลสองขั้นตอนนี้ใน developer handoff

## ข้อจำกัดที่ยังคงอยู่

ชื่อใหม่ของตระกูลอื่น รุ่นใหม่ สูตรใหม่ ตัวเลือกที่ไม่รู้ขนาด/แพ็ก หรือชุดหลาย SKU ยังคงต้องใช้หลักฐานเพิ่มเติม Parser รองรับศัพท์ที่กำหนดไว้และข้อมูลครบ ไม่อ่านคำใหม่ที่กำกวมแล้วเดาความหมาย ไม่มี fuzzy match และไม่ใช้ยอด BI ที่ลงตัวเป็นเหตุผลรับรอง mapping ผลจับคู่อัตโนมัตินี้ใช้เฉพาะตารางคัดลอก AdaSmart; general product catalog/status และการนำเข้ารหัสต้นทางยังเป็นขั้นตอนเดิม

เมื่อยืนยัน exact rule ใหม่อย่างถูกต้อง กฎนั้นเก็บใน repository ใช้ซ้ำหลัง restart/deploy และเพิ่ม profile ได้ในตระกูลที่ parser เข้าใจ หากแก้ parser ต้องเพิ่ม algorithm version และ regression tests ไม่ใช้การแก้ exact name รายวันแทนการทบทวนสาเหตุ

## Rollback

ย้อน commit ของ matcher และการต่อเข้าบริการคัดลอก จะกลับไปใช้ exact catalog/override เดิมได้ทันที ไม่ต้องย้อนข้อมูลคำสั่งซื้อ/ฐานข้อมูล เพราะงานนี้ไม่เปลี่ยน source schema หรือเขียนข้อมูล production กฎ SKU/แพ็กที่ผู้ใช้ยืนยันไว้ก่อนงานนี้ยังอยู่เหมือนเดิม เก็บ private before/after audit และผล reviewer นอก Git สำหรับตรวจย้อนกลับ
